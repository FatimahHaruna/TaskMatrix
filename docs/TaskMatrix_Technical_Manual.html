01

Introduction & Architecture Overview

1.1 Purpose & Scope

TaskMatrix is a full-stack task management web application built on the MERN stack (MongoDB, Express.js, React, Node.js). Its defining feature is the Eisenhower Matrix — a four-quadrant prioritisation system that categorises tasks by urgency and importance, guiding users toward deliberate, effective decision-making about their workload.

This manual is the single authoritative technical reference for the engineering team. It covers every file in the repository: what the file does, why it exists in its current form, how it interacts with other parts of the system, and the key code patterns it embodies. Use it when onboarding, debugging, extending features, or planning refactors.

The document reflects the codebase as it existed at the time of writing (May 2026). All code snippets are extracted verbatim from the source files.

1.2 The Eisenhower Matrix

The Eisenhower Matrix (also known as the Urgent-Important Matrix) divides tasks into four quadrants based on two axes:

QuadrantIDUrgencyImportanceStrategy
Q1 — Do Firstq1UrgentImportantHandle immediately
Q2 — Scheduleq2Not urgentImportantBlock dedicated time
Q3 — Delegateq3UrgentNot importantDelegate if possible
Q4 — Eliminateq4Not urgentNot importantDrop or defer

In TaskMatrix, tasks are created in or dragged between quadrants. The AI engine further assists by automatically suggesting the correct quadrant based on keyword analysis of the task title and notes.

1.3 System Architecture

TaskMatrix follows a classic three-tier architecture: a browser-based React SPA as the presentation layer, a Node.js/Express REST API as the application layer, and MongoDB as the data layer.

In development, Vite's built-in proxy rewrites all requests matching /api/* to http://localhost:5000, which eliminates CORS issues between the dev servers. In production, the compiled React bundle would be served from a CDN or the same origin as the API.

Key architectural decisions:

  • Stateless JWT authentication — the server issues a signed token on login; subsequent requests carry it in the Authorization header. No session store is needed.
  • Owner-scoped data — every task document carries an owner field (ObjectId ref to User). All queries filter by owner: req.user._id, ensuring strict per-user data isolation.
  • Soft-delete pattern — deleted tasks are marked deleted: true rather than physically removed, enabling a Trash page with restore and permanent-delete actions.
  • Context API state management — global state (auth + tasks) is managed via two React contexts backed by the API, with a local-state fallback for guest users.
  • AI as a layer, not a dependency — the AI engine is isolated to aiController.js and uses an in-memory keyword classifier. It can be swapped for a live Claude/OpenAI call without touching any other file.

02

Technology Stack

This section explains every major library and technology used in TaskMatrix — what it is, why it was chosen, and how it is used in the codebase.

2.1 Node.js & Express.js

Node.js is a JavaScript runtime built on V8 that executes JavaScript outside the browser. It uses an event-driven, non-blocking I/O model, making it well-suited for I/O-heavy web servers that handle many concurrent connections without thread contention.

Express.js is the de facto standard web framework for Node.js. It provides a thin layer of routing, middleware composition, and request/response helpers without imposing a heavy opinionated structure. In TaskMatrix, Express handles:

  • CORS headers (via the cors middleware package)
  • JSON body parsing (express.json())
  • Route mounting for three API namespaces: /api/auth, /api/tasks, /api/ai
  • A global error handler registered last in the middleware chain

Express middleware functions follow the signature (req, res, next). When a middleware calls next(), Express passes control to the next function in the chain. Calling next(err) skips to the error handler. This pattern is used by the protect auth middleware to gate protected routes.

2.2 MongoDB & Mongoose ODM

MongoDB is a document-oriented NoSQL database. Data is stored as BSON (binary JSON) documents grouped into collections. Unlike relational databases, there is no fixed schema enforced at the database level — schema validation is handled by Mongoose in the application layer.

TaskMatrix uses MongoDB for several reasons: its document model maps naturally to JSON API payloads, it handles arrays of subdocuments (comments, activity logs) gracefully without join tables, and it integrates seamlessly with Mongoose's JavaScript-native API.

Mongoose is an Object Document Mapper (ODM) that adds:

  • Schemas — define field types, defaults, validators, and indexes in JavaScript
  • Models — provide a query API (Model.find(), Model.findOneAndUpdate(), etc.)
  • Middleware (hooks) — pre('save') and post('save') hooks run before/after document persistence. TaskMatrix uses a pre('save') hook on User to hash passwords.
  • Virtuals — computed properties not persisted to the database. The isLocked virtual on User is an example.
  • Instance methods — custom methods on document instances. user.comparePassword(plain) uses bcrypt to verify a plaintext password against the stored hash.
ℹ
select: false Several fields on the User schema carry select: false. This means Mongoose omits them from query results by default. To retrieve them, a query must explicitly opt in with .select('+password'). This is used for password, passwordResetToken, and passwordResetExpires.

2.3 JSON Web Tokens (JWT)

JWT is an open standard (RFC 7519) for transmitting claims between parties as a compact, URL-safe token. A JWT consists of three Base64URL-encoded sections separated by dots: header.payload.signature.

  • Header — algorithm and token type ({ "alg": "HS256", "typ": "JWT" })
  • Payload — claims. TaskMatrix stores { "id": "<user ObjectId>" }
  • Signature — HMAC-SHA256 of header + payload using JWT_SECRET

On successful login or registration, the server calls signToken(user._id) which signs a token with a 30-day expiry. The client stores this in localStorage under the key tm_token. Every subsequent API request attaches it as Authorization: Bearer <token>. The protect middleware verifies the signature and expiry, then loads the user from the database and attaches it to req.user.

JWTs are stateless — the server does not store tokens. This means tokens cannot be individually revoked before expiry. For a production hardening roadmap, consider maintaining a token denylist in Redis or switching to short-lived access tokens with refresh tokens.

2.4 bcryptjs Password Hashing

Passwords must never be stored in plaintext. bcrypt is an adaptive hashing function specifically designed for passwords. It incorporates a salt (random data mixed in before hashing) and a cost factor (work factor) that controls how computationally expensive each hash computation is.

TaskMatrix uses bcryptjs, a pure-JavaScript implementation of bcrypt that runs without native bindings. The cost factor is set to 12, which produces hashes that take roughly 0.3–1 second to compute on modern hardware — fast enough for user-facing login but slow enough to make brute-force attacks impractical.

The hashing occurs in the Mongoose pre('save') hook on the User model. It only runs when the password field is actually modified (this.isModified('password')), which prevents re-hashing on unrelated profile updates. Password verification uses bcrypt.compare(plaintext, hash), which is timing-safe.

⚠
findByIdAndUpdate bypasses hooks The lockout counter resets in authController.js use User.findByIdAndUpdate() rather than user.save() intentionally — this bypasses the pre-save hook and avoids re-hashing the already-hashed password.

2.5 React 18 & JSX

React is a declarative UI library that renders component trees to the DOM. In React 18, the root is created with ReactDOM.createRoot(), which enables concurrent features including automatic batching of state updates.

JSX is a syntax extension that allows HTML-like markup inside JavaScript. Vite's React plugin (@vitejs/plugin-react) transforms JSX to React.createElement() calls at build time using Babel or SWC.

Key React patterns used throughout TaskMatrix:

  • Functional components — all components are functions, not classes
  • useState / useEffect / useCallback / useRef — the standard hooks for state, side effects, memoised callbacks, and DOM refs
  • useContext — accesses AuthContext and TaskContext without prop drilling
  • Controlled inputs — form fields bind their value to state and update via onChange
  • Conditional rendering — JSX uses ternary (? :) and short-circuit (&&) expressions to show/hide UI
  • StrictMode — main.jsx wraps the app in <React.StrictMode>, which double-invokes effects and renders in development to surface side-effect bugs

2.6 Vite Build Tool

Vite is a next-generation front-end build tool that uses native ES modules in development (no bundling step) and Rollup for production builds. This results in near-instant cold starts and fast HMR (Hot Module Replacement).

In TaskMatrix, client/vite.config.js configures two things:

  1. The @vitejs/plugin-react plugin, which enables JSX transformation and React Fast Refresh
  2. A dev-server proxy: all requests to /api/* are forwarded to http://localhost:5000. This means the React app can call /api/tasks without CORS issues during development — both origins appear the same to the browser.
client/vite.config.js
export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    proxy: {
      '/api': {
        target: 'http://localhost:5000',
        changeOrigin: true,
      },
    },
  },
});

The changeOrigin: true option rewrites the Host header of proxied requests to match the target, which prevents some server-side host validation rejections.

2.7 React Router v6

React Router v6 provides declarative client-side routing. The app uses BrowserRouter (HTML5 history API), Routes, and Route elements to define the route tree in App.jsx.

Key v6 features used:

  • <Navigate> — declarative redirects. Used for the / and * catch-all routes (both redirect to /login).
  • useNavigate() — programmatic navigation hook. Used in Sidebar, LoginPage, and WelcomePage to navigate after actions.
  • useLocation() — returns the current location object, including state. Used by RequireAuth to remember where the user was trying to go before being redirected to login.
  • Nested route guards — the custom RequireAuth wrapper component renders a spinner while loading, redirects to /login if unauthenticated, or renders children if authenticated.

2.8 Axios HTTP Client

Axios is a promise-based HTTP client for the browser and Node.js. It provides a cleaner API than fetch, automatic JSON serialisation/deserialisation, and interceptors.

TaskMatrix creates a single Axios instance in client/src/services/api.js with baseURL: '/api'. A request interceptor runs before every outgoing request to attach the JWT token:

client/src/services/api.js — interceptor
api.interceptors.request.use((config) => {
  const token = localStorage.getItem('tm_token');
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

All API calls chain .then(r => r.data) to unwrap the Axios response envelope, so callers receive the raw server response body. The helper objects (authApi, taskApi, aiApi, authApiExtra) group related calls and serve as an interface boundary — if the API URL structure changes, only api.js needs updating.

2.9 @hello-pangea/dnd Drag-and-Drop

@hello-pangea/dnd is an actively maintained fork of the widely-used react-beautiful-dnd library. It provides accessible, physics-accurate drag-and-drop for lists and boards.

Three components from this library are used:

  • DragDropContext — wraps the entire board. Its onDragEnd callback fires when the user releases a drag. It receives a result object with source (origin droppable + index) and destination (target droppable + index).
  • Droppable — marks a region as a valid drop target. Each quadrant column is a Droppable with droppableId set to the quadrant ID ('q1', 'q2', etc.).
  • Draggable — makes each task card draggable. Requires a unique draggableId (the task _id) and an index.

When a drag ends, QuadrantBoard.onDragEnd calls moveTask(draggableId, destination.droppableId, destination.index) on the TaskContext. The context immediately updates local state (optimistic update) and then fires a PUT /api/tasks/:id call to persist the new quadrant and order.

2.10 Context API

React's built-in Context API provides a mechanism for sharing state across the component tree without passing props through every intermediate level (prop drilling). TaskMatrix uses two contexts:

  • AuthContext — holds the current user object, the loading flag, and action functions: login, register, loginAsGuest, logout, updateUser.
  • TaskContext — holds the tasks array, the trash array, loading state, and all mutation functions: createTask, updateTask, deleteTask, restoreTask, permanentDelete, toggleComplete, addComment, moveTask.

Both contexts export a custom hook (useAuth, useTaskContext) that throw an error if called outside their provider, which catches configuration mistakes early.

The provider hierarchy in App.jsx is: BrowserRouter > AuthProvider > TaskProvider > Routes. TaskProvider wraps inside AuthProvider because TaskContext depends on useAuth() to know whether to load from the API or operate in guest mode.

2.11 CSS Custom Properties & Dark Mode

TaskMatrix uses a comprehensive CSS custom property (CSS variable) system defined in client/src/index.css. All colour decisions, spacing radii, shadows, and typography values are expressed as variables, making the design system easy to audit and extend.

Dark mode is implemented by toggling the class dark-mode on the <html> element. A selector html.dark-mode then overrides the root-level variables:

:root {
  --bg: #fafaf9;   /* light background */
  --ink: #0a0a0a;  /* light foreground */
}
html.dark-mode {
  --bg: #0f0f0e;
  --ink: #f0ede8;
  /* … other overrides … */
}

Because all component styles reference variables rather than hard-coded values, the entire UI repaints automatically when the class is toggled. The dark mode preference is persisted to localStorage under the key tm-dark-mode and applied in main.jsx before the first React render, eliminating the flash of wrong theme.

2.12 AI Engine

The AI engine in server/controllers/aiController.js is a deterministic keyword classifier. It is deliberately designed to be swappable — the comment at the top of the file says "swap suggestQuadrant / suggestSubtasks with real Claude/OpenAI API calls by updating only these functions."

The classifier maintains four keyword lists:

  • URGENCY_KW — words implying time pressure (tonight, asap, deadline, urgent, …)
  • IMPORTANCE_KW — words implying goal alignment (exam, thesis, career, interview, …)
  • DELEGATE_KW — words implying tasks suited for others (pick up, errand, book, arrange, …)
  • ELIMINATE_KW — words implying low value (optional, someday, hobby, browse, …)

Detection logic applies priority rules: Eliminate wins if no urgency/importance signal; delegate wins for urgent+non-important delegatable tasks; Q1 for urgent+important; Q2 for non-urgent+important; Q3 for urgent+non-important; Q4 as default.

An in-memory Map-based cache with 5-minute TTL and 500-entry cap prevents redundant computation for repeated queries. Cache keys are formed from the normalised title and notes strings.

Backend Code Explained

3.1 server.js — Entry Point

The Express application is bootstrapped in server/server.js. This file is the first module Node.js executes when the server starts.

server/server.js
require('dotenv').config();        // load .env into process.env
const express = require('express');
const cors    = require('cors');
const connectDB     = require('./config/db');
const errorHandler  = require('./middleware/errorHandler');

const app = express();
connectDB();                          // establish MongoDB connection

app.use(cors({ origin: process.env.CLIENT_URL || 'http://localhost:5173' }));
app.use(express.json());             // parse JSON request bodies

app.use('/api/auth',  require('./routes/auth'));
app.use('/api/tasks', require('./routes/tasks'));
app.use('/api/ai',    require('./routes/ai'));

app.get('/api/health', (req, res) => res.json({ status: 'ok' }));
app.use(errorHandler); // must be last — catches errors thrown by routes

const PORT = process.env.PORT || 5000;
app.listen(PORT, () => console.log(`Server running on http://localhost:${PORT}`));

Important ordering details:

  • dotenv.config() must be the first call so that all subsequent modules can access process.env variables.
  • connectDB() is called before any routes are registered, ensuring the database connection is established (or the process exits) before the server begins accepting traffic.
  • app.use(errorHandler) is registered last — Express error-handling middleware (four-argument functions) only intercept errors if they are the last middleware in the chain.
  • The CORS middleware restricts allowed origins. In a multi-environment deployment, CLIENT_URL should be set to the production frontend URL.

3.2 config/db.js — Database Connection

Database connection logic is separated into its own module to keep server.js clean and to make it easy to mock in tests.

server/config/db.js
const mongoose = require('mongoose');

const connectDB = async () => {
  try {
    const conn = await mongoose.connect(process.env.MONGO_URI);
    console.log(`MongoDB connected: ${conn.connection.host}`);
  } catch (err) {
    console.error(`MongoDB connection error: ${err.message}`);
    process.exit(1); // terminate if DB unreachable at startup
  }
};

The process.exit(1) on connection failure is intentional — a server that cannot reach its database should not begin serving traffic, as all subsequent requests would fail.

3.4 Controllers

authController.js

Handles all authentication operations. Each export is an Express route handler (async (req, res) => {}).

validatePassword(password) — enforces the password policy before creating or resetting accounts: minimum 8 characters, at least one uppercase letter, one digit, and one special character. Returns a descriptive error string or null on success.

register — validates required fields and password strength, checks for email uniqueness (returns 409 on conflict), creates the user (triggering the pre-save hook to hash the password), and responds with a signed JWT + user object.

login — fetches the user with .select('+password +loginAttempts +lockUntil') to opt in to normally-hidden fields, checks the lockout timestamp, compares the password, and either increments the failure counter or resets it on success. The lockout is applied after 5 consecutive failures and lasts 15 minutes.

ℹ
Why findByIdAndUpdate for counters? After a successful login, the failure counters are cleared using User.findByIdAndUpdate() rather than user.save(). This bypasses all Mongoose middleware, which means the bcrypt pre-save hook does not run and the already-hashed password is not re-hashed.

getMe — returns req.user as-is. The protect middleware already loaded the user from the database and attached it to the request object.

updateMe — accepts a whitelist of updatable fields (displayName, timezone, notificationPrefs, aiPrefs, darkMode) and applies them with findByIdAndUpdate. Also regenerates avatarInitials if displayName changes.

forgotPassword — generates a cryptographically random 32-byte token with crypto.randomBytes(32), stores its SHA-256 hash on the user document (not the raw token), and sets a 1-hour expiry. The raw token would be sent in an email reset link in production. The response always returns the same success message regardless of whether the email exists, preventing email enumeration attacks.

resetPassword — receives the raw token from the client, hashes it, and looks up the user by matching hash + unexpired expiry. If found, sets the new password (triggering the pre-save hash hook via user.save()), clears the reset fields and lockout counters, and returns a new JWT.

taskController.js

All task operations are scoped to the authenticated user via owner: req.user._id on every query. This is the primary data isolation mechanism.

getTasks — finds all non-deleted tasks for the owner, sorted by quadrant then order then creation date. Returns an array.

getTrash — finds all deleted tasks for the owner, sorted by deletion date descending.

createTask — spreads the request body and forcibly sets owner to the authenticated user's ID (client cannot override this). Adds an initial activity log entry.

updateTask — first fetches the task to check ownership (404 if not found or not owned). Then builds an activity entry, with special handling for quadrant changes: logs the human-readable label names of origin and destination quadrants. Uses $push to append the activity entry atomically.

softDeleteTask — sets deleted: true and deletedAt atomically with findOneAndUpdate, also pushing an activity entry. Returns 404 if the task is not found or not owned by the requester.

restoreTask — clears deleted and deletedAt, pushes a restore activity entry.

permanentDelete — calls findOneAndDelete, which physically removes the document. Ownership is verified in the query predicate.

toggleComplete — fetches the task, flips the completed boolean, sets or clears completedAt, pushes an activity entry for either completion or reopening, and saves.

addComment — appends a new comment and an activity entry using a single $push on two array fields atomically.

reorderTasks — accepts an array of { id, quadrant, order } objects and runs them as parallel findOneAndUpdate calls. All updates include the ownership predicate for safety. This is called by the drag-and-drop system after a card is dropped.

aiController.js

Implements three endpoints. All share the same in-memory cache infrastructure.

Cache implementation: A Map called aiCache stores entries keyed by a normalised string of title + notes. Each entry is { data, ts }. The getCached(key) function checks TTL (5 minutes) and deletes stale entries on access. setCache(key, data) clears the entire map if it exceeds 500 entries, preventing unbounded memory growth.

suggest — calls detectQuadrant(title, notes) and suggestTitleImprovement(title). Introduces a 350ms artificial delay (setTimeout) to simulate async AI API latency, which makes the UI loading state visible during development.

subtasks — calls suggestSubtasks(title, notes) which uses keyword matching to produce a context-appropriate 3–4 item checklist (e.g., essay tasks vs. presentation tasks vs. exam tasks).

misclassify (FR-413) — compares the currentQuadrant the task is placed in against what detectQuadrant would suggest. Returns an isMisclassified boolean plus the suggested quadrant and explanation. Used by TaskModal to show a warning banner when opening an existing task.

3.5 Routes

Routes are thin wiring layers that connect HTTP method+path combinations to controller functions. They also apply middleware selectively.

routes/auth.js

Note that GET /me and PUT /me apply the protect middleware but registration, login, forgot-password, and reset-password do not — they are intentionally public endpoints. The GET /search endpoint is protected (only authenticated users can search for teammates by email) and returns only safe public fields (_id, displayName, email, avatarInitials).

routes/tasks.js

All task routes are mounted in server.js under /api/tasks and all share the protect middleware applied at the router level (applied in server.js — note: actually applied per route in routes/tasks.js via the parent router setup). The route ordering matters: GET /trash and POST /reorder must appear before GET /:id-style routes to prevent trash and reorder being interpreted as ID parameters.

routes/ai.js

All three AI routes are POST endpoints — they accept title and optionally notes in the request body. The AI routes do not require authentication in the current implementation (no protect middleware on the ai router), though they should be gated in production to prevent abuse.

3.6 Middleware

middleware/auth.js — protect

The JWT authentication guard. It reads the Authorization header, validates the Bearer prefix, verifies the token, loads the user from the database, and attaches it to req.user. If any step fails (missing header, invalid token, user deleted from DB), it returns 401 immediately without calling next().

server/middleware/auth.js
const protect = async (req, res, next) => {
  const header = req.headers.authorization;
  if (!header || !header.startsWith('Bearer '))
    return res.status(401).json({ message: 'Not authenticated' });
  try {
    const token   = header.split(' ')[1];
    const decoded = jwt.verify(token, process.env.JWT_SECRET || 'tm_dev_secret');
    req.user = await User.findById(decoded.id).select('-password');
    if (!req.user) return res.status(401).json({ message: 'User not found' });
    next();
  } catch {
    res.status(401).json({ message: 'Invalid token' });
  }
};

middleware/errorHandler.js — Global Error Handler

A four-argument Express middleware that catches any error forwarded via next(err) from route handlers. Returns the error status code (defaulting to 500) and the error message. In development mode, it also includes the stack trace in the response to aid debugging.

server/middleware/errorHandler.js
const errorHandler = (err, req, res, next) => {
  const status = err.statusCode || 500;
  res.status(status).json({
    message: err.message || 'Internal Server Error',
    ...(process.env.NODE_ENV === 'development' && { stack: err.stack }),
  });
};

Note that most controller functions currently use inline try/catch and call res.status(...).json(...) directly rather than forwarding to this handler via next(err). This handler therefore primarily catches synchronous throws or middleware errors not wrapped in try/catch.

Authentication Flow

7.1 Registration

1. Client — POST /api/auth/register with displayName, email, password, timezone
2. Server — validate required fields → validate password strength
3. Server — check email uniqueness (User.findOne); 409 if taken
4. Server — User.create() → triggers pre-save hook → bcrypt.hash(password, 12)
5. Server — respond 201 with { token: signToken(user._id), user: { ... } }
6. Client — store token in localStorage['tm_token'], set AuthContext user, navigate to /welcome

7.2 Login & Account Lockout

1. Client — POST /api/auth/login with email, password
2. Server — User.findOne({ email }).select('+password +loginAttempts +lockUntil')
3. Server — if lockUntil > now: respond 423 with remaining time
4. Server — user.comparePassword(password) → bcrypt.compare()
5a. Password WRONG — increment loginAttempts; if ≥5, set lockUntil = now + 15min → 423; else 401 with attempts remaining
5b. Password CORRECT — User.findByIdAndUpdate({ loginAttempts: 0, $unset: { lockUntil: 1 } }) → respond 200 with token
6. Client — store token, set user in context, navigate to /board
⚠
Counter reset uses findByIdAndUpdate Step 5b uses findByIdAndUpdate rather than user.save() to avoid triggering the bcrypt pre-save hook, which would re-hash the already-hashed password stored in the user document.

7.3 JWT Lifecycle

Tokens are signed with HS256 (HMAC-SHA256) using the JWT_SECRET environment variable. The payload contains only { id: <user ObjectId> }. Tokens expire after 30 days.

Per-request flow on protected routes:

1. Client — Axios interceptor reads localStorage['tm_token'] and sets Authorization: Bearer <token>
2. Server — protect middleware reads Authorization header, validates Bearer prefix
3. Server — jwt.verify(token, JWT_SECRET) — throws if expired or invalid signature
4. Server — User.findById(decoded.id).select('-password') — attaches to req.user
5. Server — calls next() to hand off to the route controller

If the token is missing, malformed, expired, or the user has been deleted, a 401 Unauthorized response is returned and the route controller is never called.

On the client side, a 401 response from any API call should trigger a logout (clear token, redirect to login). Currently this is handled by AuthContext's getMe error handler on startup — catching mid-session 401s in the Axios interceptor would be a recommended enhancement.

7.4 Password Reset Flow

1. User — opens ForgotPasswordModal in LoginPage, enters email
2. Client — POST /api/auth/forgot-password with { email }
3. Server — if user found: crypto.randomBytes(32) → rawToken; store sha256(rawToken) as passwordResetToken + 1h expiry; [production: email link]; [dev: return rawToken in response]
4. User — enters the rawToken and a new password in step 2 of the modal
5. Client — POST /api/auth/reset-password with { token: rawToken, password }
6. Server — hash the token, find user by hash + unexpired; validate new password strength
7. Server — user.password = newPassword; clear reset fields; clear lockout; user.save() → pre-save hook hashes new password
8. Server — respond with new JWT token so user is automatically logged in
⚠
Production change required The current implementation returns resetToken directly in the API response for development convenience. Before production deployment, remove resetToken from the response and send it exclusively via email.

7.5 Guest Sessions

Guest mode allows unauthenticated users to explore the board interface without creating an account. The loginAsGuest function in AuthContext:

  1. Clears any existing tm_token from localStorage
  2. Creates a synthetic user object: { _id: 'guest', displayName: 'Guest', email: '', isGuest: true }
  3. Stores it in localStorage['tm_guest']
  4. Sets user in AuthContext to this object

TaskContext detects user.isGuest === true and skips all API calls, operating entirely on in-memory state. Guest tasks exist only until the page is refreshed. When the guest clicks the logout icon, both tm_token and tm_guest are cleared.

ℹ
Note: The current LoginPage does not expose a "Continue as guest" button in the UI — the loginAsGuest function exists in the context but is not wired to any visible control. This was likely intentional product decision to encourage account creation.

Key Patterns & Conventions

8.1 Data Ownership & Isolation

Every task document has an owner field set to the authenticated user's ObjectId. All database queries in taskController.js include owner: req.user._id in the filter predicate. This means:

  • A user can never retrieve, update, or delete another user's tasks — the query will return null and the controller will respond 404
  • The owner field has an index for query performance as user task counts grow
  • The client cannot override the owner: createTask spreads req.body but then forcibly sets owner: req.user._id, which takes precedence

This pattern — server-enforced, per-user data scoping — is the primary security control for data privacy. The JWT only identifies the user; the ownership filter on every query enforces isolation.

8.2 Soft-Delete Pattern

Tasks are never physically removed by the normal delete flow. Instead:

  • DELETE /api/tasks/:id sets { deleted: true, deletedAt: new Date() }
  • GET /api/tasks filters with { deleted: { $ne: true } }
  • GET /api/tasks/trash filters with { deleted: true }
  • PATCH /api/tasks/:id/restore clears both fields
  • DELETE /api/tasks/:id/permanent calls findOneAndDelete for true removal

Benefits: users get a recoverable trash experience; the activity log is preserved for audit; analytics based on completedAt remain accurate for deleted tasks until permanent removal.

8.3 Optimistic UI Updates

TaskContext implements optimistic updates for drag-and-drop and task completion to keep the UI feeling responsive:

  • moveTask — updates the local tasks array immediately, then fires the API call. If the API call fails, the local state and server state diverge until the next reload. A reload() function is exposed to force a fresh fetch.
  • deleteTask — removes the task from tasks and adds it to trash locally, then calls the API. No rollback on API failure.
  • toggleComplete — in API mode, waits for the server response before updating state (not optimistic), ensuring completedAt is set by the server.

The trade-off is simplicity over perfect consistency. For a production app with multiple concurrent users or unreliable connectivity, implementing rollback-on-failure would be recommended.

8.4 AI Response Caching

The AI controller implements a simple in-memory cache to avoid redundant computation for repeated identical requests (e.g., the misclassify check fires every time a task modal opens).

const aiCache = new Map();
const CACHE_TTL = 5 * 60 * 1000; // 5 minutes in milliseconds

function getCached(key) {
  const entry = aiCache.get(key);
  if (!entry) return null;
  if (Date.now() - entry.ts > CACHE_TTL) { aiCache.delete(key); return null; }
  return entry.data;
}
function setCache(key, data) {
  if (aiCache.size > 500) aiCache.clear(); // prevent memory leak
  aiCache.set(key, { data, ts: Date.now() });
}

Cache keys are built from the lowercased, trimmed title and notes concatenated with a ||| separator plus a suffix for the endpoint (|suggest or |subtasks). The cache is process-local — it resets on server restart and is not shared across multiple Node.js workers. For production, move this to Redis for durability and multi-process sharing.

8.5 Activity Log Pattern

Every task carries an activity array that functions as an append-only audit log. Entries are added via MongoDB's $push operator, which is atomic and does not risk race conditions from concurrent reads and writes.

An activity entry is added for every meaningful state change: creation, updates (with special messaging for quadrant moves), soft deletion, restore, completion toggle, and comments. The activity tab in TaskModal renders these entries in reverse-chronological order so users can see the full history of a task.

Importantly, when updateTask in the controller detects a quadrant change, it generates a human-readable log entry using the quadrant label map:

const labels = { q1: 'Do First', q2: 'Schedule', q3: 'Delegate', q4: 'Eliminate' };
activityEntry.detail = `Moved from ${labels[existing.quadrant]} to ${labels[req.body.quadrant]}`;

8.6 Error Handling

Backend: Most controller functions use inline try/catch blocks and directly call res.status(x).json({ message }). The global errorHandler middleware serves as a safety net for uncaught synchronous throws. In development (NODE_ENV=development), stack traces are included in the JSON response.

Frontend: The aiService.js wrapper catches all AI API errors and returns null or empty arrays, so the UI degrades gracefully (no AI suggestions shown, no error thrown). Context methods in TaskContext also catch errors silently in some cases (e.g., moveTask swallows API errors to not disrupt the drag-and-drop UX). More structured error handling — surface errors via the Toast system — is a recommended improvement.

File Organisation Convention

Each major concern lives in its own file. Controllers contain only business logic — they import models and respond. Routes contain only wiring (no business logic). Middleware contains only cross-cutting concerns. This separation makes it straightforward to locate and modify any behaviour without reading unrelated code.

On the frontend, pages are one-per-route and import components. Components import from the ui/ layer for primitives and from contexts for data. Services handle all HTTP calls and are the only files that import Axios. This layered import graph prevents circular dependencies and makes mocking straightforward for testing.
